# Eyle 2.7.3 — Revision 55.1 Windows PID hotfix

## Root cause

Revision 55 still used `os.kill(pid, 0)` as a process-existence probe in two paths:

- `engine/queue.py`, reached by `/status`, `/health`, CLI status, and interrupted-job recovery;
- `engine/process_limiter.py`, reached while cleaning cross-process LLM limiter leases.

That pattern is appropriate on POSIX. On Windows it is not a harmless signal-0 probe and can terminate the target process. Because the Worker and Flask server share the same process in `main.py serve`, polling `/status` could inspect the Worker's own PID and silently terminate Eyle with exit code 0 before Flask returned the response.

## Fix

A new `engine/process_utils.py` centralizes PID liveness checks:

- the current PID is accepted immediately without any system call;
- POSIX keeps the standard signal-0 check with bounded error handling;
- Windows opens a process handle with `SYNCHRONIZE` access and calls `WaitForSingleObject(handle, 0)`;
- access-denied or inconclusive probes are treated conservatively as possibly alive, preventing unsafe lease deletion or duplicate job recovery;
- the Windows path never calls `os.kill` and never sends a signal.

Both `queue.py` and `process_limiter.py` now delegate to this shared helper. Limiter cleanup also probes each unique PID only once per cleanup pass.

## Connected hardening

The same review found and corrected three adjacent failure modes:

1. Legacy SQLite timestamps without timezone information could raise an aware/naive `datetime` subtraction error and break `/status`. They are now interpreted as UTC.
2. An invalid heartbeat timestamp was shown as stale by statistics but was not recovered by `recuperar_interrompidos`, which could leave a job permanently in `processing`. Invalid heartbeats are now treated as interrupted.
3. A corrupt or out-of-range PID could raise `OverflowError` in the POSIX probe and break health checks. It now returns inactive safely.

## Validation

- `python -m compileall -q engine tests` passed.
- 225/225 executable non-web tests passed.
- One Flask-dependent test module was skipped because Flask was unavailable in the packaging environment.
- New tests prove that the current PID, queue statistics, and limiter cleanup do not call `os.kill`; the simulated Windows branch delegates only to the Windows probe.

## Remaining architectural note

PID liveness is still only one signal. Heartbeat age and lease expiry remain the authoritative recovery fallbacks, which limits PID-reuse and permission edge cases.
