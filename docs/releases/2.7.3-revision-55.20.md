# Eyle 2.7.3 — Revision 55.20

**Revision:** `55.20-real-audit-coverage`  
**Date:** 2026-08-05

Revision 55.20 separates the minimum audit gate from the real reach of the investigation. A grounded answer is no longer presented without a deterministic disclosure of how much of the project was actually observed.

## Public coverage record

Every successful `project_audit` publishes a system-generated record:

```json
{
  "coverage": {
    "inventory_complete": true,
    "code_files_total": 38,
    "code_files_read": 7,
    "code_files_fully_read": 7,
    "critical_components_total": 6,
    "critical_components_read": 5,
    "tests_executed": false,
    "tests_passed": false,
    "test_run_attempts": 0,
    "docs_used": 2,
    "level": "targeted"
  }
}
```

The record is calculated from the structured project inventory, fresh Evidence Registry entries, deterministic catalog/Scout selections, final claim evidence IDs, and actual task actions. The model cannot override these values.

## Coverage levels

- `none`: no source-code evidence was read;
- `partial`: some code was read, but the minimum structural audit gates were not all satisfied or the inventory was partial;
- `targeted`: the inventory is complete and all structural audit gates were satisfied without reading every source file completely;
- `complete`: every inventoried source file was read completely.

`complete` means complete coverage of the inventoried source files under the configured tree depth, limits, filters, ignore rules, and secret protections. It does not mean branch coverage or proof that all runtime behavior is correct.

## Honest disclosure

After claim validation and grounding, Eyle prepends a deterministic disclosure such as:

```text
Targeted analysis completed.
5 critical components were reviewed.
7 of 38 inventoried source files were read.
Tests were not executed.
It is not possible to claim that the project is completely free of bugs.
```

This text is generated by code rather than by the Finalizer, so a fluent model response cannot hide limited reach or invent test execution.

## Historical release statements

A release note may be cited as history, for example “revision 55.13 recorded 294 passing tests,” only when:

- the statement is explicitly attributed to a revision, release, README, changelog, or documentation;
- the referenced evidence is fresh documentation evidence;
- the claim does not present that historical count as current operational status.

Current statements that tests pass still require a successful `run_tests` action in the current task.

## Required regression matrix

Revision 55.20 verifies that:

- large inventories preserve `engine/`, `llm/`, and `tests/`;
- README-only reading cannot complete a general audit;
- one evidence item cannot satisfy a large-project audit;
- global “no critical issues” claims remain blocked without proof;
- “294 tests passing” remains blocked without `run_tests`;
- an old release can be cited explicitly as historical documentation;
- a one-file project remains fast and can receive `complete` inventoried-source coverage.
