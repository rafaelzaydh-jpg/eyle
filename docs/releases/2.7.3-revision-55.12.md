# Eyle 2.7.3 — Revision 55.12

## Autonomous grounding recovery

Revision 55.12 removes a false dependency on the user from the Agent conclusion path.

Previously, a final answer rejected repeatedly by deterministic semantic grounding became `needs_user`. A normal reply such as `continue` restored the same state, generated the same unsupported conclusion, failed again, and created another pending ID. The conversation state was preserved, but the task could not make progress.

### Single autonomy rule

The Agent now follows one rule for projects of every size:

- internal validation failures are repaired internally;
- only information or authorization that truly depends on the user becomes `needs_user`;
- exhausted semantic repair produces a safe, reduced answer;
- an unrecoverable technical failure becomes `failed`.

Project size changes only how much evidence must be read. It does not change this behavior.

### Actionable semantic repair

The deterministic verifier now produces compact repair feedback for the next Agent decision. For each rejected claim it exposes:

- the exact claim;
- objective error codes;
- unsupported anchors;
- evidence IDs mapped to that claim.

This replaces the previous generic message that only said unsupported statements existed.

### Conservative automatic fallback

After the configured no-progress threshold:

1. claims already accepted by the verifier are kept;
2. rejected claims are removed;
3. an explicit limitation is added;
4. when no original claim survives, the response reports only verified file ranges;
5. the fallback is verified again before publication.

If this second verification unexpectedly fails, the Agent returns `failed` with `SEMANTIC_GROUNDING_FAILED`. No pending user action is created.

### Stable pending identity

Human-facing pending actions now preserve their ID when the same valid task is resumed. A new ID is generated only for a new, expired, mismatched-project, or structurally invalid pending action.

## Regression coverage

- rejected claim feedback includes the exact unsupported `os.remove` anchor;
- three repeated invalid finals terminate successfully through the safe fallback without a pending action;
- supported claims survive while unsupported claims are removed;
- a resumed valid pending action keeps the original ID.
