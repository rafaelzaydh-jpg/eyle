# Eyle 2.7.3 — Revision 55.13

## Typed grounding autonomy

Revision 55.13 keeps the autonomous recovery introduced in 55.12, but removes an excessive limitation: the project is no longer treated as the only truth the Agent is allowed to express.

The project is now treated as **observed state**. The Agent may derive conclusions, form testable hypotheses, make technical decisions, and recommend new designs without pretending those choices were already present in the code.

### Five epistemic claim types

The conclusion verifier separates statements into:

- `fact`: objective description of observed state; requires fresh evidence;
- `inference`: conclusion derived from observations; requires an evidence basis;
- `hypothesis`: uncertain possibility that may introduce new technical ideas and should be tested when possible;
- `decision`: future choice made by the Agent; may introduce new values, files, or implementation paths;
- `recommendation`: proposed improvement; does not need to preexist in the project.

Unannotated assertive statements remain `fact` by default, preserving the strict protection against invented objective details.

### Agent protocol

Project finals may include `claim_annotations`. Only non-factual statements need annotation. Each annotation may contain the exact claim, type, supporting evidence IDs, and a short basis.

The local deterministic classifier remains as a compatibility fallback for older model outputs and naturally modal phrases such as “pode”, “recomendo”, or “vou”.

### Typed recovery

When a conclusion is rejected:

1. the repair feedback identifies the rejected claim and its epistemic type;
2. valid reasoning, hypotheses, decisions, and recommendations are preserved;
3. only claims that violate the rule for their own type are rewritten or removed;
4. internal validation failure never becomes a fake user dependency.

This avoids both extremes: hallucinated facts are still blocked, but the Agent is not reduced to a literal project reader.

## Regression coverage

- invented objective facts remain blocked;
- recommendations may introduce new files and values;
- decisions do not need to already exist in the project;
- inferences require a real evidence basis but may contain derived values;
- hypotheses remain allowed with explicit uncertainty;
- safe fallback removes unsupported facts while preserving valid recommendations;
- exhausted repair still finishes without `needs_user`.
