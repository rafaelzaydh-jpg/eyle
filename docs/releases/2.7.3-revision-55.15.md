# Eyle 2.7.3 — Revision 55.15

**Revision:** `55.15-evidence-integrity-and-job-identity`  
**Date:** 2026-08-05

Revision 55.15 closes the false-success paths discovered after 55.14. A project answer can no longer be published merely because it is long, plausible, or structurally valid.

## Implemented

- Project utility validation now requires observed, fresh evidence. Missing evidence returns `PROJECT_NOT_READ`.
- Legacy `consulta`, `dicas`, and `visao_geral` pipelines now build typed evidence from actual reads and run both the utility gate and typed grounding before persistence or publication.
- Unsupported project claims return `UNGROUNDED_PROJECT_ANALYSIS` and are never added to the conversation.
- The legacy read fallback preserves evidence IDs and grounding metadata instead of publishing with `evidence_ids: []`.
- `engine/worker.py` treats either `status=failed` or `agente_status=failed` as a failed queue job.
- Persistent Agent tasks reject reuse of the same `task_id` with another objective, mode, project hash, or source job using `REQUEST_CONTEXT_MISMATCH`.
- SQLite now has a persistent `queue_instance_id`; the browser discards tracked jobs when the database instance changes.
- A newly submitted browser job never inherits terminal status, progress, or work summary from an older job with the same numeric ID.
- Executed `find_symbol` misses are recorded as negative evidence, allowing a grounded conclusion that a requested symbol was not found.

## Intentionally fail-closed

- A legacy overview of a project larger than the configured full-read limits now returns `PROJECT_NOT_READ`. It does not analyze only `estrutura.json` and pretend the source was read.
- Old browser job state created before queue instance IDs is discarded once. It cannot be migrated safely because the old state contains no trustworthy database identity.

## Remaining limitations

- Deterministic typed grounding is conservative and lexical; it reduces unsupported claims but is not a universal semantic proof system.
- Real behavior still needs benchmark validation against the user's local LLM and representative large repositories.
- Flask-dependent web tests require Flask in the final installation environment.
